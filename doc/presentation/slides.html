운영 인시던트 대응 에이전트

운영자가 장애 증상을 채팅으로 물으면, 에이전트가 모니터링 지표와 대응 매뉴얼(runbook)을 직접 조사해 번호 절차로 조치를 답한다.

route잡담/장애→planMCP Prompt→gate→ researchMCP Tool·Resource⇄replan_checkrunbook 판별→ analysis→write⇄validate→finalize

베이스 구성

  • FastAPI + LangGraph StateGraph, SSE 스트리밍, Vue 채팅 UI
  • MCP 서버 2개(ops/docs) — 모니터링 Tool, runbook Resource, 진단 Prompt
  • LLM: OpenAI gpt-4o-mini(판단) / gpt-4o(답변 작성)

직접 돌려보며 찾은 약점

  • runbook을 키워드 첫 매칭 1개로 선택, 모르는 표현은 전부 db-down
  • 시스템명이 없으면 무조건 auth-service 진단
  • 검증은 "30자 이상 + 1) 포함"만 확인
  • graph.py 단일 파일, 중복 코드 3곳, 테스트 0개

02 · 핵심 개선

runbook 판별: 키워드 규칙 → 의미 검색

Before — KeywordIncidentClassifier

text = 모든 시스템 알림을 한 문자열로 합침
for kw, type in RULES:      # latency, pool, cpu ...
    if kw in text: return [type]   # 첫 매칭 1개
return ["db-down"]          # 그 외 전부

After — RagIncidentClassifier

probes = [시스템별 알림 문장]  (없으면 사용자 질문)
hits = kb.search(probes, kind="runbook", k=1)  # 임베딩 1회 batch
→ 시스템마다 top-1 청크의 metadata.incident_type
→ 중복 제거, 최대 3개 runbook을 MCP Resource로 조회

지식베이스 (agent/rag)

  • runbook 8종 → 요약 청크 + 절차 청크, metadata에 incident_type
  • text-embedding-3-small, 코사인 검색 (청크 55개라 외부 벡터DB 없이 구현)
  • 인덱스 디스크 캐시: 키 = (임베더, 코퍼스 해시) → 재기동 시 비용 0, runbook 수정 시 자동 재색인
  • 새 장애 유형 = .md 파일 추가만 (코드 수정 없음)
  • INCIDENT_CLASSIFIER=keyword|rag 토글 → 같은 코드로 A/B 측정

기술상태이번 과제에서 한 일

단위 테스트신규pytest 28개 — 노드·RAG·그래프 전체 경로, 무한 루프 방지·미등록 시스템 처리
